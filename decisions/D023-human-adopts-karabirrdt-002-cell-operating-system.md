## Adopted architecture resolutions

## 3. Resolved architecture decisions from the review

### 3.1 Fake settlement
Adopt the middle position:

> deterministic settlement fixtures/test doubles are required **inside**
> reconciliation testing, but there is no standalone fake-settlement product or
> milestone.

They must exercise replay, duplicate receipt, mismatch, cancellation, pending,
failure/replacement and interruption. They do **not** prove real-chain behavior.

### 3.2 Company Core Evaluation vs Verification vs Human Decision

Preserve four distinct questions:

`Company Core Evaluation`
= Did the Result usefully address the Need?

`Verification`
= What does an accountable review establish about a Claim?

`domain Decision`
= Does an authorized Human accept/reject/defer that Claim for this context?

`Economic authorization`
= Does the prospective Agreement's named Human acceptance basis authorize this
economic consequence?

Rules:
- Company Core Evaluation never releases payment by itself.
- Claim-dependent economic release requires the relevant Verification +
  contextual domain Decision.
- `DEFER` never releases a Claim-dependent consequence.
- Reimbursement, stipend, cancellation fee or objectively completed obligation
  need not manufacture a Claim solely to use `domain_decisions`; it still
  requires the explicit bounded Human approval named prospectively in the
  Agreement.
- AI never becomes final acceptance or treasury-signing authority.

This resolves an internal tension in the Kimi R2 output, which both says
`domain_decision` is required for economic release and later allows
Agreement-configured simpler Human approval paths.

### 3.3 Decentralization target
Day-30 target:

`D1 = demonstrated Cell stewardship with founder oversight`

Plus:

`provider-neutral D2 seam = prepared/testable`

Not claimed:

`D2 real-fund autonomous treasury achieved`

### 3.4 Web3
Web3 is not removed. It is converted into a **meaningful conditional experiment**.

If the selected case demonstrates a property worth testing:
- bind one signer/recipient wallet to an Actor;
- associate one testnet Safe with a provider-neutral TreasuryReference;
- create an authorized EconomicInstruction;
- have required Human Safe owners inspect/sign;
- transfer an existing test asset;
- observe directly from chain;
- reconcile the receipt into CZ;
- test one failure/replacement path.

Cut from 30-day critical path:
- EAS publication;
- Request Network integration;
- passkey/embedded wallet optimization;
- native CZ ERC-20/token;
- custom escrow/module/guard;
- federation/appchain;
- public speculative token.

These remain future hypotheses, not rejected forever.

### 3.5 Case timing
Case selection moves into PLAN, before implementation commits architecture around
a hypothetical participant.

Contact/enrollment remains separately Human-gated.

### 3.6 Shared membership
Invite / accept / contextual role / revoke / leave / visibility must be inspected
and, if actually missing, minimally extended before external Cell use.

`delegation ≠ membership`

## Adopted adversarial acceptance assertions

## 4. Mandatory adversarial acceptance assertions

Kimi's strongest additional attacks are incorporated as acceptance criteria
rather than atomised first-class tasks:

1. Test `Company Core Evaluation = USEFUL/PASS` while `domain Decision = REJECT`;
   Claim-dependent EconomicInstruction must remain blocked.

2. The deterministic settlement test must explicitly document at least five
   chain/network failure modes it simulates but does not validate.

3. Any wallet path must record which blockchain concepts an ordinary participant
   is forced to understand. If non-signing participants need crypto literacy,
   H3 is not satisfied.

4. Every Marcos intervention in the real episode is classified as:
   `AUTHORITY / RELATIONSHIP / TROUBLESHOOTING / UNPLANNED-RESCUE`.

5. Test abandonment:
   what happens when a Cell has commitments but no currently active steward?

6. If Web3 GO:
   test signer loss/replacement, wrong network/asset/recipient and receipt mismatch.
