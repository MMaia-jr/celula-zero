## Question tested

> Can the economic and non-economic reference cases be represented mechanically,
> end-to-end, using existing standards plus at most the four CZ semantic classes
> retained by G-C1, without collapsing provenance, evidence, verification,
> authority, decision, outcome or social projection?

The candidate CZ classes under test are:

```text
cz:Need
cz:Claim
cz:Verification
cz:Decision
```

## Standards substrate

The representation composes:

- W3C PROV / PROV-O for agents, activities, entities, plans, attribution,
  association, delegation, derivation, bundles and qualified roles;
- ActivityStreams 2.0 for identifiable social activities such as Offer, Accept,
  Reject, Follow, Create and Announce, and for actor/object/target/context/result;
- ODRL 2.2 when explicit policy terms, permissions, prohibitions, duties,
  constraints or agreements are actually required;
- A2A only when software-agent task/message/artifact interoperability is actually
  present.

No substrate above is treated as proof of truth, legitimacy, quality or trust.

## Mechanical profile rules

G-C2 intentionally avoids introducing a fifth CZ class.

The profile can remain mechanically reconstructible using:

1. the four CZ classes;
2. standard PROV relations and qualified roles;
3. ActivityStreams activities and `context`;
4. ODRL policy objects only when terms require them;
5. A2A task/artifact objects only when agent interoperability requires them;
6. a small controlled value/role vocabulary.

### Controlled role values

Qualified PROV Usage/Association may use role values such as:

```text
claim-subject
evidence
criteria
authority
candidate
selected
verification-input
commitment-scope
outcome-basis
privacy-policy
```

These are profile values, not new classes.

### Controlled result values

`prov:value` or an equivalent serialization value may carry bounded statuses such
as:

```text
PASS
FAIL
PARTIAL
INCONCLUSIVE

SELECT
ACCEPT
REJECT
CONTINUE
```

The value never replaces the provenance of the activity that generated the
record.

## Invariants under test

The representation must preserve all of the following:

```text
source ≠ evidence
Claim ≠ source
Evidence ≠ Verification
Verification ≠ Decision
Decision ≠ Outcome
Proposal ≠ Commitment
Commitment ≠ Agreement
Activity ≠ Contribution
provenance ≠ truth
visibility ≠ reputation
social projection ≠ private/source record
```

A Decision must remain attributable to an authority-bearing activity/context.
A Verification must remain criteria-bound and independently reconstructible.
An Outcome remains a contextual Claim until separately evidenced/verified.

# Case A — Economic coordination

## Scenario

A bounded frontend need is opened. Four providers submit proposals. One proposal
is selected under explicit criteria and authority. Work is performed, an artifact
is delivered, the deliverable is verified, an authorized acceptance decision is
made, settlement may occur, and a later real-world consequence may be recorded
as an outcome claim.

This is a representation fixture, not authorization to solicit providers or move
funds.

## Mechanical record ledger

| ID | Native type / pattern | CZ class? | Mechanical role |
|---|---|---:|---|
| `A-BUNDLE-1` | `prov:Bundle` | no | episode/context container |
| `A-NEED-1` | `prov:Entity` + optional AS2 Object | `cz:Need` | attributed bounded need |
| `A-OPP-1` | `as:Offer` | no | opportunity around `A-NEED-1`; `as:context=A-NEED-1` |
| `A-PROP-1..4` | `as:Offer` + `prov:Plan` / optional `odrl:Offer` | no | four attributed proposals targeted at `A-OPP-1` |
| `A-CRIT-1` | `prov:Plan`/Entity | no | selection criteria |
| `A-AUTH-1` | `prov:Entity`/Plan/policy | no | authority/governance basis |
| `A-SELECT-ACT` | `prov:Activity` | no | uses proposals + criteria + authority with qualified roles |
| `A-DEC-1` | `prov:Entity` | `cz:Decision` | selection decision generated by `A-SELECT-ACT`; value `SELECT` |
| `A-COMMIT-1` | `as:Accept` | no | provider explicitly accepts exact selected proposal/scope |
| `A-AGREE-1` | optional `odrl:Agreement` | no | machine-readable terms when useful; not the commitment event |
| `A-FUND-1` | external payment/escrow record/activity | no | funding mapping only when required |
| `A-WORK-1` | `prov:Activity` + optional A2A Task mapping | no | execution under selected Plan/Commitment |
| `A-ART-1` | `prov:Entity` / optional A2A Artifact | no | generated deliverable |
| `A-CLAIM-ACT-1` | `prov:Activity` | no | uses artifact as `claim-subject`; generates deliverable claim |
| `A-CLAIM-1` | `prov:Entity` | `cz:Claim` | contestable claim that the artifact satisfies the scoped deliverable |
| `A-REVIEW-1` | `prov:Activity` | no | uses Claim=`subject`, Artifact/source=`evidence`, criteria=`criteria` |
| `A-VER-1` | `prov:Entity` | `cz:Verification` | generated review record; bounded status such as `PASS` |
| `A-ACCEPT-ACT` | `prov:Activity` | no | authorized decision activity using verification + commitment scope |
| `A-DEC-2` | `prov:Entity` | `cz:Decision` | `ACCEPT / REJECT / CONTINUE`; distinct from `A-VER-1` |
| `A-SETTLE-1` | payment/refund mapping | no | settlement under applicable terms |
| `A-OUTCOME-ACT` | `prov:Activity` | no | creates outcome statement from observed consequence and basis |
| `A-CLAIM-2` | `prov:Entity` | `cz:Claim` | `kind=outcome`; may itself be verified or remain unverified |
| `A-PROJECT-1` | derived AS2 Object/Activity + PROV derivation | no | permitted public Social Projection |

## Selection without a new relation class

`A-SELECT-ACT` can mechanically preserve the selection using qualified PROV
Usage:

```text
A-PROP-1  role=candidate
A-PROP-2  role=selected
A-PROP-3  role=candidate
A-PROP-4  role=candidate
A-CRIT-1  role=criteria
A-AUTH-1  role=authority
```

The activity generates `A-DEC-1`.

No `Selection`, `Authority`, `Criteria` or `Proposal` CZ class is required.

## Commitment without a Commitment class

`A-COMMIT-1` is an identifiable ActivityStreams `Accept`.

The CZ profile interprets it as a Commitment pattern only when all required
context is reconstructible:

- actor is explicit;
- accepted object is the exact proposal/plan/terms version;
- scope is bounded;
- actor has sufficient authority for the context.

If formal policy terms are useful, `A-AGREE-1` may be an ODRL Agreement.

This preserves:

```text
Proposal ≠ Commitment
Commitment ≠ Agreement
```

## Evidence and verification without collapse

The artifact/source remains a PROV Entity.

Its use as evidence is contextual:

```text
A-REVIEW-1
  uses A-CLAIM-1 role=subject
  uses A-ART-1   role=evidence
  uses A-CRIT-1  role=criteria
  generates A-VER-1
```

Therefore:

```text
A-ART-1 ≠ A-VER-1
source ≠ evidence ≠ verification
```

## Decision and outcome without collapse

The acceptance activity uses the verification as an input; it does not inherit
the verification's authority automatically.

```text
A-ACCEPT-ACT
  uses A-VER-1    role=verification-input
  uses A-COMMIT-1 role=commitment-scope
  uses A-AUTH-1   role=authority
  generates A-DEC-2
```

A later consequence is represented separately as `A-CLAIM-2`, `kind=outcome`.

Therefore:

```text
Verification ≠ Decision ≠ Outcome
```

## Social Projection

A projection activity may use only records permitted by privacy/consent policy,
generate an ActivityStreams representation and preserve derivation to the
underlying episode.

Private proposals, identities, payment details, security notes or full evidence
do not become public merely because the projection is public.

### Case A result

`REPRESENTABLE / PASS`

No fifth CZ class is required.

# Case B — Non-economic coordination

## Scenario

A project/community has a bounded need. A person offers a scoped contribution,
accepts the scope, delegates bounded work to one or more software agents, produces
an artifact, makes a contribution claim, receives evaluation, and the context may
make an acceptance decision. No payment or economic right is assumed.

## Mechanical record ledger

| ID | Native type / pattern | CZ class? | Mechanical role |
|---|---|---:|---|
| `B-BUNDLE-1` | `prov:Bundle` | no | episode/context container |
| `B-NEED-1` | `prov:Entity` + optional AS2 Object | `cz:Need` | real bounded need |
| `B-OPP-1` | `as:Offer` | no | opportunity around Need |
| `B-PROP-1` | `as:Offer` + `prov:Plan` | no | attributed proposal to contribute |
| `B-COMMIT-1` | `as:Accept` | no | explicit bounded undertaking |
| `B-HUMAN-1` | `prov:Person` | no | responsible human |
| `B-AGENT-1` | `prov:SoftwareAgent` | no | delegated software agent |
| `B-WORK-1` | `prov:Activity` + optional A2A Task | no | contribution work |
| `B-ART-1` | `prov:Entity` / optional A2A Artifact | no | produced artifact |
| `B-CLAIM-ACT-1` | `prov:Activity` | no | generates contribution claim |
| `B-CLAIM-1` | `prov:Entity` | `cz:Claim` | claim that work/artifact counts as contribution in context |
| `B-REVIEW-1` | `prov:Activity` | no | optional criteria-bound evaluation |
| `B-VER-1` | `prov:Entity` | `cz:Verification` | optional verification result |
| `B-DEC-ACT-1` | `prov:Activity` | no | optional authorized accept/reject decision |
| `B-DEC-1` | `prov:Entity` | `cz:Decision` | optional legitimate decision |
| `B-OUTCOME-ACT` | `prov:Activity` | no | creates statement about observed consequence |
| `B-CLAIM-2` | `prov:Entity` | `cz:Claim` | `kind=outcome` |
| `B-NEXT-1` | AS2 Follow/Offer/etc. | no | later relation/opportunity if observed |
| `B-PROJECT-1` | derived AS2 Object/Activity + PROV derivation | no | bounded Social Projection |

## Delegated agent work

PROV already supports software agents and delegation provenance.

The profile can preserve that `B-AGENT-1` acted on behalf of the responsible
human/organization for bounded work, and can qualify the relevant association or
delegation by activity/role.

When actual remote-agent interoperability is present, an A2A Task/Artifact may be
mapped to the same work/artifact episode.

A2A is not required merely because an AI was used.

## Contribution without a Contribution class

`B-WORK-1` is an Activity.

Whether it counts as a Contribution is contextual and contestable.

`B-CLAIM-1` states that it counts as contribution in `B-BUNDLE-1`. If acceptance
matters, a Verification and/or Decision may confirm, reject or leave that claim
inconclusive.

Therefore:

```text
Activity ≠ Contribution
```

No Contribution class is required.

## Optionality test

The model remains coherent when no payment exists.

It also remains coherent when:

- no formal ODRL Agreement is needed;
- no remote A2A interaction is needed;
- verification is not required by the context;
- a separate Decision is not required because no legitimate state change depends
  on acceptance.

Optional absence does not force placeholder objects.

### Case B result

`REPRESENTABLE / PASS`

No fifth CZ class is required.

`FIFTH CLASS JUSTIFIED: NO`

## Result interpretation

G-C2 strengthens, but does not fully validate, the G-C1 minimum.

The current result is:

```text
4 semantic classes are sufficient for both reference cases
+
standard relations/activities/policies
+
a bounded controlled role/status vocabulary
```

This is narrower than a new protocol and broader than merely reusing standards
without a profile.

The CZ-specific property remains the disciplined composition that keeps Need,
Claim, Verification and Decision semantically distinct while treating
contribution, evidence, outcome, trust and social visibility as contextual
patterns rather than universal truth/reputation objects.

## What this gate does not prove

G-C2 does not prove:

- that two independent implementations serialize the profile identically;
- that JSON-LD/RDF is the required production encoding;
- that ODRL terms have legal force in a jurisdiction;
- that PROV records establish truth or legitimacy;
- that ActivityStreams privacy is sufficient as a security boundary;
- that A2A is required for ordinary AI-assisted work;
- that any blockchain is required;
- that the profile creates external utility;
- that users understand or want the model;
- that the profile should yet be implemented.
