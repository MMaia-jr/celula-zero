## 5. Reuse-first rule

Before creating any primitive, route family, service, protocol, storage layer,
or major package, classify the need:

`ADOPT / MAP / COMPOSE / EXTEND / MISSING`

Tie-breaker:

`ADOPT → MAP → COMPOSE → EXTEND`

### ADOPT

Use a mature maintained standard/tool/service/library when it already preserves
the required property with acceptable authority, privacy, provenance,
portability, licensing and exit.

### MAP

Use an existing CZ representation or capability without changing its semantics.

### COMPOSE

Connect existing capabilities into the lived product flow.

### EXTEND

Make the smallest change only after an observed concrete property loss.

### MISSING

Use only when neither existing CZ capabilities nor mature external technology
can preserve the required property.

For every proposed `EXTEND` or `MISSING`, record:

`OBSERVED BLOCKAGE`
`→ LOST USER POSSIBILITY / PROPERTY`
`→ WHY ADOPT FAILED`
`→ WHY MAP FAILED`
`→ WHY COMPOSE FAILED`
`→ SMALLEST EXTENSION`
`→ ACCEPTANCE TEST`

Without this chain:

`DO NOT BUILD`

## 8. Target Founder experience

Codex should assemble the smallest coherent browser journey that gives Marcos a
single understandable place to work.

### 8.1 Enter / resume

After authentication, Marcos can answer:

- Where am I?
- What is the current project/state?
- What was I doing?
- What matters now?
- What can I do next?

Do not require architecture literacy.

### 8.2 Express

Marcos can write a real Dream, Need, concern, question or decision in ordinary
language.

Preserve it as an Original Record where the existing model supports that
property.

Do not silently convert the Human statement into truth, identity, Claim,
Evidence, Project or Human Direction.

### 8.3 Perceive / understand

The system can assemble a candidate understanding from existing authorized
context.

Requirements when AI interpretation is used:

- attribution;
- source/basis where materially relevant;
- uncertainty;
- Human correction;
- `ACCEPT / EDIT / REJECT` or equivalent;
- no silent promotion to Human Direction.

### 8.4 Discover

Surface a small set of useful possibilities from resources already accessible
in the current context.

Discovery may include:

- canonical decisions/results;
- existing Projects/Needs;
- artifacts;
- capabilities;
- existing tools;
- relevant people already legitimately represented;
- Cells;
- AI capabilities;
- possible next actions;
- alternate framings.

Start with existing relations, structured data, ordinary text search and
bounded AI synthesis.

No embeddings/vector infrastructure without observed retrieval property loss.

Preserve:

`RELEVANCE ≠ TRUST`

`DISCOVERY ≠ RELATIONSHIP`

### 8.5 Choose / compose

Marcos chooses a direction.

The product should show what capabilities/resources already exist before asking
for new construction.

Where existing primitives are currently spread across `/genesis`,
`/company-core`, `/workbench` or other pages, compose or link them into one
coherent flow rather than duplicating their semantics.

### 8.6 Authorize bounded work

When work is needed, the Human can establish enough conditions to authorize it.

Reuse existing:

- Agreement;
- Commitment;
- Company Core work definition;
- Task Capsule;
- Execution Fabric;
- AI Job/AI Run;

where they preserve the required property.

Do not create a second work ontology.

### 8.7 Act

The MVP must support at least one real bounded action.

For software-engineering work, the first MVP does NOT require building a
browser-hosted autonomous coding sandbox if existing Task Capsule / Codex
handoff is sufficient.

A valid first composition may be:

`ONLINE HUMAN DECISION`
`→ CODEX-READY BOUNDED TASK CAPSULE`
`→ CODEX EXECUTION IN AUTHORIZED WORKSPACE`
`→ RESULT PACKAGE RETURN`
`→ ONLINE HUMAN REVIEW`

If this handoff is materially too burdensome in lived use, that burden can
become observed property loss for a later direct integration.

Preserve:

`CODEX EXECUTION ≠ HUMAN DECISION`

### 8.8 Result / consequence

The Human can inspect what actually happened.

Do not auto-promote:

`AI OUTPUT → RESULT`

or:

`RESULT → EVIDENCE`

or:

`EVIDENCE → VERIFICATION`

### 8.9 Human Decision

Marcos remains the authority for the episode's legitimate decision.

### 8.10 Regenerate / return

The session closes with:

- what changed;
- what remains unresolved;
- what became newly possible;
- what dependency increased/decreased;
- what should happen next.

After leaving and returning later, Marcos should recover enough context to
continue without manually reconstructing the episode.

The MVP should feel like one product even if several existing subsystems remain
underneath it.

Codex may:

- add a coherent Founder Workspace / Home;
- reorganize navigation;
- create composition/view-model layers;
- reuse existing server actions/data functions;
- create thin adapters;
- improve copy and affordances;
- remove duplicated user-facing steps when semantics remain preserved;
- provide progressive disclosure for advanced internals.

Codex should NOT:

- rewrite working domain semantics merely for UI uniformity;
- duplicate canonical data into a second product store;
- require the Founder to know internal IDs;
- expose SQL/terminal as normal product UX;
- make architecture terms the primary navigation model.

The preferred visual/product question is:

> What does Marcos need to understand or do next?

not:

> Which internal entity/table/module does Marcos want to inspect?

## 17. Result classes

`PASS`

One real Founder episode is usable online end-to-end enough to produce and
retain observable capacity/consequence.

`PARTIAL`

The assembled product creates material Founder capacity but one bounded
property still requires manual bridging or repair.

`FAIL`

The assembled experience does not materially increase the Founder's ability to
understand, decide or act, or it cannot preserve required authority/provenance.

`INCONCLUSIVE`

A precondition/runtime issue prevents meaningful evaluation.

Additional lived classifications may coexist:

`NO MATERIAL GAIN`
`CONCERN ESCALATED`
`WRONG FRAMING`
`INSUFFICIENT CONTEXT`

Do not force PASS.
